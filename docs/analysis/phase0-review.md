## 1. 「事実」「推測」「改善提案」の分類

### 1.1 分類の考え方

| 区分 | 定義 | 判定基準 |
|---|---|---|
| 事実 | コードを直接読む、またはgrep/awk等の機械的な突合で断定できる内容 | JSの実行結果が決定的（ブラウザ実行なしでも一意に定まる）、またはファイルの中身をそのまま確認したもの |
| 推測 | コードからは断定できず、外部システム（GAS本体）の挙動や、開発者の意図、実際のブラウザ操作結果を仮定している内容 | GAS側の実装、開発の経緯・意図、実機での見た目や操作感など、リポジトリの外側や未実行の領域に関する記述 |
| 改善提案 | 事実・推測を踏まえた分析者（Claude）の設計判断・推奨 | 「〜の余地がある」「〜を検討する価値がある」「〜が望ましい」等の評価的表現 |

### 1.2 修正した箇所（推測を事実として書いていたもの）

レポート全体を再点検した結果、**「推測に基づく事実」を無条件の断定として書いていた明確な誤りは見つかりませんでした**（当初レポートは概ね「〜可能性がある」「〜と推測されるが確認不可」といった適切なヘッジを使っていました）。ただし、逆方向の問題として、**静的コード解析だけで100%断定できる内容に対して、不要に弱いヘッジ（「可能性が高い」「要動作確認」）を使っていた箇所が3件**あり、これは分析の確信度を実態より低く見せてしまっていたため、以下の通り修正しました。

| 該当箇所 | 修正前の表現 | 修正後の表現 | 修正理由 |
|---|---|---|---|
| 8.3 #1（出題形式フィルタ） | 「〜可能性が高い（要動作確認）」 | 「確定事実（静的コード解析のみで断定可）」 | `MODE_FILTER_OPTIONS[subject]`のオブジェクトキー参照はJSの仕様上決定的であり、`subject`の値（`index.html`のoption値で確定）とキー集合が一致しないことはコードを読むだけで100%確定する。ブラウザ実行による確認は不要 |
| 8.3 #2（中東mapId不一致） | 「〜表示される可能性がある」 | 「確定事実」 | `getMapConfig`のフォールバックロジックは条件分岐であり、`MAP_CONFIGS`にキーが存在しないことをCSV全行の`awk`抽出で確認済みのため、挙動は一意に定まる |
| 8.3 #3（hidden未除外） | 「〜表示され続けている可能性がある」 | 「確定事実」 | フィルタ条件`status !== "inactive"`と実際のCSV値`hidden`の比較は文字列比較であり、結果は決定的 |

### 1.3 「推測」に分類すべきだが、レポート内で十分にラベル付けされていなかった箇所

| 該当箇所 | 内容 | 修正内容 |
|---|---|---|
| 8.6 #3 | 「後から構造を変えるとGAS/シート側の集計ロジックも連鎖的に変更が必要になる」 | GAS本体のロジックが実際に存在するかは本リポジトリから確認不可であるため、「（推測: 断定はできないが）GAS/シート側に集計ロジックが既に実装されていれば」という条件付きの表現に修正 |

### 1.4 「改善提案」に分類すべき箇所（参考: 変更は不要と判断したもの）

モジュール分析表の`◎/○/△/✕`評価、8.7「触らない方が良い箇所」、10章の🟢🟡🔴判定は、いずれも分析者による設計評価であり、性質上「事実」ではなく「改善提案／評価」です。レポート内では見出しや文脈（「評価」「改善点」等の列名）で区別されており、事実と混同する表現にはなっていなかったため、追加修正はしていません。

## 2. 分析漏れの確認

Phase0では`find`コマンドで**プロジェクト内の全ファイル（.git除く、対象リポジトリはGit未管理）を一覧化済み**であり、フォルダ・ファイルレベルでの見落としはありません。一方、内容レベルで「存在は把握したが中身を精査していない／実行して確認していない」ものがありました。本レビューで追加確認したものと、依然未確認のまま残るものを分けて報告します。

### 2.1 本レビューで追加確認したファイル

| ファイル | 確認結果 |
|---|---|
| `.vscode/settings.json` | 中身は `{}` のみ。プロジェクト固有のエディタ設定は無く、分析に影響なし |
| `assets/河川クリック問題テンプレ（完全版）.txt` | 河川クリック問題を追加する際の設計メモ。**現行コードとの差異あり**（`map-river-light.svg`という現存しないファイル名を記載、CSVサンプルの`subject`が`geography`となっている等）。これは`config/modes.js`の`geography`キーが実際の科目キー体系と食い違っている（8.3 #1）ことの背景を推測する手がかりになる一次資料（後述） |

### 2.2 本レビューで追加検証した内容

| 検証内容 | 方法 | 結果 |
|---|---|---|
| 日本地理CSV全113行の`mapId`が`MAP_CONFIGS`のキーと一致するか | `awk`で`mapId`列を全抽出し重複排除、目視突合 | 全11種すべて一致（不一致なし） |
| 世界地理CSV全84行の`mapId`が`MAP_CONFIGS`のキーと一致するか | 同上 | `world_regions_edu`のみ不一致（8.3 #2として報告済み） |
| 各CSVの`status`列に実際にどの値が使われているか | `awk`で`status`列を全抽出し重複排除 | japan_geo: `active`のみ／world_geo: `active`と`hidden`／history: `active`のみ。**`inactive`は3ファイルとも1件も存在しない**（フィルタの`inactive`除外ロジックは現状のデータでは一度も発火しない、実質デッドパス） |
| 日本地理の都道府県/河川/山脈/半島/海岸のsvgAreaId(s)がSVG内に実在するか | 各id/classについて対応SVGファイルへ`grep`で存在確認（47都道府県class、河川2件、山脈7件、半島14件、海岸6件、計76件） | 全件一致（不一致なし） |
| 世界地理の国名/州/地形のsvgAreaId(s)がSVG内に実在するか | 世界国名41件（map-world.svg）、アジア11件（map-asia.svg）、ヨーロッパ11件（map-europe.svg）、世界の地形18件（map-world-physical.svg）を`grep`で存在確認 | **世界の地形のうち`australia`のみ不一致を新規発見**（8.3 #7として追加）。他77件は全て一致 |

### 2.3 依然として未確認・未検証のまま残っている範囲（今回のスコープ外として報告）

| 項目 | 状態 | 備考 |
|---|---|---|
| `style.css`全595行の内容 | 冒頭80行のみ通読、残りはクラス名のgrep抽出による部分確認 | 表示崩れ等の視覚的な問題はこの方法では検出できない |
| 11枚のSVGファイルの視覚的レイアウト・クリック領域の妥当性 | id/classの存在確認のみ実施、座標・形状・重なりなどは未確認 | 例えば「クリック可能領域が小さすぎる」といった使い勝手の問題は検出対象外 |
| 実際のブラウザでの起動・操作確認 | 一切未実施 | 本レポート・レビューは100%静的コード解析（読解・grep・awk）によるもの。動的な確認（実際にページを開いて操作する）は今回のPhase0では行っていない |
| GAS本体（.gsファイル、Apps Scriptプロジェクト） | リポジトリに含まれないため確認不可 | `services/gas-service.js`が参照するURLの先にある実装は完全にブラックボックス |
| Google Sheetsのシート構造・既存の集計/ランキング機能の有無 | 未確認 | 既存の生徒管理システム側に類似機能が既にある可能性は排除できていない（10章のランキング等の判定に影響しうる） |
| 問題データの統計（科目別・単元別・形式別の問題数分布） | 一覧化はしたが集計（件数の合計・分布）は行っていない | 出題バランスの評価が必要な場合は別途集計が要る |
| CSVファイルの実バイナリ（BOM有無・改行コード等） | `question-loader.js`がBOM除去処理を持つことから存在を示唆されるのみ | バイナリレベルの確認はしていない |

**結論**: フォルダ・ファイルの一覧という意味での「見落とし」は無し。ただし「静的読解では検出できない領域」（視覚的レイアウト、実機操作、外部システムの内部実装）が一定量残っており、これらはPhase0の性質上（コード変更禁止・調査のみ）妥当なスコープ設定だったと判断します。

## 5. 絶対に変更しない方が良い設計

| カテゴリ | 維持すべき対象 | 理由 |
|---|---|---|
| フォルダ構成 | `config / core / filters / judges / renderers / services`の6分割そのもの | 名前と実態の責務が一致しており、新規参加者でも「どこに何があるか」を推測しやすい。分割単位を変えると全modaleのimportパスが連鎖的に壊れる |
| モジュール構造 | `QUESTION_MODE_HANDLERS`（`question-screen-controller.js`）による出題形式ディスパッチテーブル方式 | 新形式追加時の変更箇所が1テーブルへのエントリ追加に閉じている。テーブル駆動をやめてif/elseに戻すと拡張性が退化する |
| モジュール構造 | `MAP_RENDERERS`（`map-click-renderer.js`）によるprefecture/line/area戦略パターン | 地図の描画方式ごとの実装が完全に分離されており、1方式の変更が他方式に波及しない。理科の地形図等、今後の地図追加もこのパターンに乗せるのが安全 |
| 責務分離 | `judges/answer-judge.js`が純粋関数群でDOMに一切依存しない設計 | 採点ロジックはテスト容易性・正確性の要であり、DOM依存を持ち込むと将来の自動テスト導入が困難になる |
| 責務分離 | `renderers/*`（出題形式別）がDOM生成のみに専念し、状態管理を`core/state.js`に委ねている構造 | View層とロジック層の分離が保たれている。renderer内に状態管理ロジックを混在させ始めると、出題形式ごとの挙動差異が追いづらくなる |
| 設計思想 | CSV駆動の問題管理（問題追加にコード変更を要さない） | 非エンジニアでも問題を追加できる現行運用の根幹。この方式をやめてコード内に問題を埋め込む設計に戻すと、運用コストが大幅に増える |
| 設計思想 | 画面遷移を`activeクラスの付け替えのみ`で管理するシンプルな設計（`core/screen-controller.js`） | 3画面という規模に対して過不足のない実装。SPAルーターの導入は現状の規模には過剰 |
| 個別ファイル | `renderers/map-click-prefecture.js` / `map-click-line.js` / `map-click-area.js`のSVG操作ロジック | 各SVGファイルのクラス名・id名と密結合しており、正しく機能している現状のロジックを不用意に変更すると、47都道府県・河川・山脈など広範囲の地図問題が同時に壊れるリスクが高い |
| 個別ファイル | `core/question-loader.js`のCSVパーサ（カンマ/タブ自動判定・クォート対応） | 地味だが作り込みが良好で、現状3CSV全てで正しく機能している。列追加程度の変更では触る必要が無い |

### 全体の目安

- **流用可能な範囲が広い領域**: 問題システム、生徒管理連携、フォルダ構成、judges層、core層 → LS総合テスト対策への移行における「土台」としての完成度は高い。
- **修正が前提になる領域**: config層のキー体系、filters層、services層（GAS送信データ構造） → これらは複数の将来機能（理科追加・ランキング・学習履歴）に横断的に影響するため、設計書で最優先に扱うべき領域。
- **新規実装が必要な領域**: UI（ランキング・履歴画面）、GAS側API（集計系） → 現設計に受け皿が無いことが分析から明確なため、設計書側で新規モジュールとして明示的に計画する必要がある。

## 8. LS総合テスト対策へ向けた最優先課題 5つ（設計上の優先順位）

コード修正の指示ではなく、**「システム設計書 Ver.1」で最初に方針を確定すべき設計判断**として選定しています。

| 順位 | 課題 | なぜ最優先か |
|---|---|---|
| 1 | **科目キー体系の統一方針を確定する**（`config/subjects.js`の`japan_geo`/`world_geo`/`history`と、`config/modes.js`の`geography`/`history`という2つの異なる分類軸をどう整理するか） | 現在の確定バグ#1の根本原因であると同時に、理科追加時に同じ設計不備を再生産しないための土台。最も影響範囲が広く、最初に決めるべき |
| 2 | **GASへの送信データ構造を再設計する方針を確定する**（`buildSavedSubjectName`の合成文字列ではなく、科目・単元・出題形式・分野を個別フィールドとして送るか） | ランキング・年度ランキング・学習履歴・苦手問題・おすすめ問題など、将来機能の半数以上がこのデータ構造に依存する。後から変えるほど移行コストが増える |
| 3 | **CSVとコード側マスタ（`MAP_CONFIGS`／SVGのid／`AREA_LABEL_MAP`）の整合性を保証する仕組みの設計方針を確定する** | 今回発見した確定バグ4件のうち3件が「CSVとコード側マスタの不整合がサイレントに実行時フォールバックする」という共通パターン。理科・地図問題強化で問題データが増えるほど再発しやすい |
| 4 | **`status`列の値と意味のライフサイクルを仕様として確定する**（`active`/`inactive`/`hidden`それぞれが何を意味し、どう扱われるべきか） | 確定バグ#3の原因であり、今後「下書き」「レビュー待ち」等の状態が増えることが予想される問題データ管理の基盤 |
| 5 | **バージョン管理（Git）導入の方針を確定する** | コード修正を伴わない意思決定だが、Phase1で「小さな単位での実装」を安全に積み重ねるための前提条件。差分管理・ロールバックが無いままでは、他の4課題の実装自体のリスクが上がる |
